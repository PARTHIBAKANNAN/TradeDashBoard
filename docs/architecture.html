01 — Topology

System topology & data plane

Three tiers. The browser never touches the broker: all secrets and the raw broker websocket live only on the backend, which diffs each tick and fans out a minimal JSON delta to all clients. A Postgres database sits off to the side — it is not part of the live-tick path at all (see Storage).

02 — Boundary

Security model

The architectural boundary is the whole point of the BFF: credentials and the broker connection are quarantined server-side.

✕Never on the frontend

API keys · Client ID · Secret Key · TOTP seed · trading PIN · access/refresh tokens · the raw broker websocket.

✓Backend-only

Loaded from .env via python-dotenv; the daily token is cached to .token_cache.json on disk (git-ignored) — not in any database.

🛡️

Corporate TLS. On a network with SSL inspection, Python's bundled CA store rejects the broker's cert. pip-system-certs routes TLS through the Windows certificate store (which holds the corporate root CA), fixing requests, the FYERS SDK, and the websocket at once. Windows-only — skipped entirely on the Linux production host.

03 — Authentication

Login method & flow

FYERS access tokens expire every 24 hours. Rather than a manual OAuth redirect every day, the backend drives FYERS' programmatic login using your own credentials + a TOTP seed — the standard headless algo-trading pattern. A newly created app requires a one-time browser consent; every day after is fully automatic.

Token acquisition — the actual fallback chain

The full 6-step TOTP dance below is the last resort, not the everyday path. Every call to get_access_token() — including the 08:45 daily cron — tries these in order and stops at the first that succeeds:

1 · same-day cached token → 2 · refresh-token grant (~15-day validity, no TOTP) → 3 · full TOTP + PIN login (steps below) → 4 · give up, wait for manual "Connect FYERS"

In practice the 6-step chain only actually runs once every ~15 days, when the refresh token itself expires — most days, step 2 alone renews the access token silently.

The full TOTP + PIN chain (step 3 above)

1

Send login OTP challenge

POST /vagator/v2/send_login_otp_v2 — the base64 login id opens a TOTP session.

# api-t2.fyers.in
{ "fy_id": base64(FY_ID), "app_id": "2" }  → request_key  (sub: totp_login)
2

Verify TOTP

POST /vagator/v2/verify_otp — code from pyotp.TOTP(seed).now(). If the first attempt lands on a 30s window boundary, it retries once with a freshly minted code a second later.

{ "request_key": …, "otp": TOTP() }  → request_key  (sub: verify_pin)
3

Verify PIN → vagator token

POST /vagator/v2/verify_pin_v2 — the base64 trading PIN yields a short-lived login access token.

{ "request_key": …, "identity_type": "pin", "identifier": base64(PIN) }
    → data.access_token  (the "vagator" bearer)
4

Obtain the OAuth auth code

POST /api/v3/token with the vagator bearer. For an authorized app this returns a redirect URL carrying the real auth_code.

# api-t1.fyers.in
Bearer <vagator_token>
{ "fyers_id", "app_id", "redirect_uri", "appType",
  "response_type": "code", "create_cookie": true }
    → Url?auth_code=…&state=dashboard
5

Exchange for the API access & refresh token

SessionModel.generate_token() POSTs to /validate-authcode with appIdHash = SHA256("client_id:secret") + the auth code.

session.set_token(auth_code)
resp = session.generate_token()
access_token, refresh_token = resp["access_token"], resp.get("refresh_token")
6

Cache & use

Both tokens are written atomically to .token_cache.json (temp file + rename, so a kill mid-write can't corrupt it), keyed off the JWT's own real exp claim — then power the REST FyersModel and the FyersDataSocket feed (CLIENT_ID:token).

One-time consent for a new app

A freshly created app is not yet authorized against your account, so step 4 returns a pre-consent token with no auth_code. Running manual_auth.py once (browser login → Allow → paste the redirected URL) authorizes the app permanently. After that, the chain above runs unattended.

04 — Data plane

Complete data-ingestion flow

Two ingestion paths feed one thread-safe in-memory state: a REST backfill at startup so no field is ever blank, and the live websocket for streaming ticks. A Broadcaster task diffs state every 250 ms and fans delta frames to all WebSocket subscribers.

A · Startup REST backfill (4 passes, all per-symbol except quotes)

FYERS' history() endpoint has no batch mode — each pass below is a loop of 170 individual REST calls, paced 50 ms apart. Only quotes() supports batching (≤50 symbols/request).

1Previous day

Daily candles (resolution:"D", ~12d) → last completed day's high / low / close for the benchmark & every stock.

2Today's ORB

30-min candles for today → C1–C4 high/low keyed by candle start-time, plus today's running high/low.

3Breakout-quality seed

5-min candles for the 09:15–09:45 opening range → candle1_high/low + the two-sided-range check (feeds the C1 quality gates).

4Quote seed

Batched quotes() (≤50/req) → an initial LTP so rows render fully before the first tick.

⚠️

Known account limitation. On this FYERS account, history() currently returns -403 Additional permission required — so passes 1–3 above return nothing in production; only the batched quote seed (pass 4) succeeds. The ORB boundaries and breakout-quality data are instead derived live from ticks (candle_aggregator.py) using the identical math, just fed from the websocket instead of REST history. If FYERS' permission is ever restored, the REST passes simply start working again — the two paths don't conflict.

B · Symbol subscription & live websocket ingestion

Yes — all 170 watchlist stocks plus the NIFTY 50 index are subscribed together on one single websocket connection, not 170 separate sockets. Before subscribing, validate_symbols() pings every symbol via a batched quotes() call and drops anything FYERS doesn't recognise — one bad/delisted ticker in the subscribe list would otherwise tear down the entire connection.

C · 250 ms WebSocket broadcast to the browser

A single Broadcaster task snapshots state every 250 ms, diffs it against the previous snapshot, and fans the minimal JSON delta (or a full snapshot on first connect / resync) to every subscriber via bounded asyncio.Queues. This is a completely separate WebSocket connection from the FYERS one above — the browser only ever talks to this backend, never to FYERS directly.

05 — Engines

Indicators & calculations

Every tick recomputes these deterministic engines in memory before the next broadcast. All functions are pure (no side effects) and unit-tested in isolation.

Engine A

Relative Strength vs NIFTY 50 (RS)

RSi,t = Δ% Stocki,t − Δ% NIFTYt

Each side is % change vs its own previous close. The single biggest input into every downstream score — positive means outperforming the index right now.

RS > 0 · Outperform RS < 0 · Underperform
Engine F

Relative Strength vs Sector

RSsector = Δ% Stock − mean(Δ% Sector members)

Each stock's fine-grained sector tag rolls up into a broader NIFTY-style group; every member's plain average % change (not volume-weighted) becomes that group's benchmark for this comparison.

Engine D

Day Range Position (%)

LTPt − TLTH − TL × 100

Where the price sits inside today's own low→high band so far (0–100%). Feeds the day-range bar, the "Extended" warning, and the momentum score's extension penalty. A zero-span guard returns 0.

Engine E

Volume-Weighted Average Price (VWAP)

VWAP = cumPV / cumVol

Ticks carry cumulative today's volume, not per-trade size — so each tick's volume delta is multiplied by that tick's LTP and added to a running (price×volume) sum, divided by running volume. A non-monotonic (stale/duplicate) volume tick is treated as a zero delta rather than corrupting the running sums.

Engine B

30-min Opening Range Breakout (C1–C4)

UpperCn = max(LTP)  ·  LowerCn = min(LTP)  over t ∈ Cn

Candles: C1 09:15–09:45 · C2 09:45–10:15 · C3 10:15–10:45 · C4 10:45–11:15. Once a candle completes, a breach of its bound triggers a signal; the newest completed candle wins over an earlier one, and a repeat tick in the same signal state doesn't re-fire. C1 additionally has to clear two quality gates below before it's allowed to fire at all.

LTP > Upper → Bull • Cn LTP < Lower → Bear • Cn
Engine C

Normalized Dual-Range Mapper

x(P) = P − minmax − min × 100

With min = min(YL, TL) and max = max(YH, TH), yesterday's and today's ranges (plus the live LTP) all map onto one shared 0–100% scale, drawn as one canvas bar.

Breakout quality gates — C1 only

C2–C4 are pure structural breaks with no filter. A C1 (opening-range) breakout additionally has to pass both of these before the signal is allowed to fire:

1

First-candle-extreme-intact

The very first 5-minute candle's low (bullish) — or high (bearish) — must still be the day's extreme so far, i.e. never undercut/overtaken since. A trend-cleanliness check: it rules out a first candle that was itself later invalidated by a bigger move the other way.

2

Two-sided range

Among the six 5-minute candles making up the 09:15–09:45 window, at least one must close red and one green. Rules out a stock that simply gapped and ran one direction non-stop for 30 minutes — no genuine range was ever established to "break out" of.

🧵

Tick-derived, not REST-derived. Because history() is broken on this account (see Ingestion), candle_aggregator.py builds the C1–C4 boundaries and the two quality-gate inputs live from the tick stream itself — same formulas, different data source. It also separately records every completed 5-minute candle across the whole session (09:15–15:30) into candle_history for future backtesting — kept in an entirely separate code path so that addition can never regress the signal logic above.

✓

Verified. The engine suite passes its unit tests — pct-change, RS, day-range, dual-range map, VWAP, ORB breakout & precedence, and the momentum score below all have dedicated test files exercised on every deploy.

06 — Composite score

Momentum score & the "Recommended" tag

A single 0–100 composite that ranks every currently-signaled stock, computed identically in two places from one ported formula: client-side (JS) for the on-screen tag, and server-side (Python) on a schedule for automated checkpoint alerts.

Hard filter — applied before any scoring

⛔

Score is forced to 0 if there's no active signal, or if the signal direction disagrees with NIFTY's own move right now — a Bull signal needs NIFTY %change ≥ 0; a Bear signal needs NIFTY %change ≤ 0. On a day NIFTY is anywhere near flat, this alone disqualifies roughly half the signaled universe outright, regardless of how strong the individual setup looks.

🏅Confidence floor

Only the top 3 stocks scoring ≥ 60 get the Recommended tag. Below that, the tag simply doesn't appear — a quiet/indecisive market can legitimately produce zero picks all day.

⏱Checkpoint-locked

Recomputed every tick underneath, but the displayed picks only re-lock every 30 minutes (09:45, 10:15, 10:45…) to avoid flickering — so the tag can be up to ~30 minutes stale relative to the live number.

📈

What this score does not know. It measures how strong the current move looks right now — it has no concept of chart structure, prior peaks, or "this already failed once today." A stock mid-double-top can still score well right up until it reverses.

08 — Persistence

What's actually stored in the database

Almost nothing about the live market data is persisted. Everything in Calculations and Recommended above — LTP, RS, VWAP, signals, momentum scores — lives only in RAM (MarketState) and is wiped on every backend restart.

DataWhere it livesSurvives a restart?
Live LTP, RS, VWAP, signals, momentum scoresMarketState — plain Python dicts in RAMNo
5-min OHLC candles, whole sessionPostgres — candle_historyYes (backtest groundwork)
Simulated (paper) orders & positionsPostgres — paper_ordersYes
Simulated wallet balancePostgres — paper_walletsYes
FYERS access/refresh tokensLocal disk file — .token_cache.json (not the DB)Yes, same-day / ~15-day
Dashboard login sessionSigned cookie (itsdangerous) — no server-side session tableYes, ~14 days per cookie

💽

In short: the database's job is trade record-keeping and future backtest data, not live market state. The entire signal/scoring engine could run with zero database connectivity at all — Postgres only gets involved once you place a simulated order or once a 5-minute candle needs recording.

09 — Concurrency

Process model — one service, not microservices

There is exactly one deployed backend service (tradedashboard-backend, one systemd unit, one Python interpreter). Inside that single process, a few concurrent workers all read and write the same in-memory MarketState object, coordinated by one threading.RLock — there is no separate "fetcher" service handing data to a separate "storage" service over a network hop.

🔁Main asyncio event loop

Serves HTTP + the browser's /ws/stream WebSocket, runs the Broadcaster task, owns the paper-trading Postgres connection pool.

🧵FYERS ingest thread

One dedicated background thread running the blocking FYERS websocket client — ingests every tick and runs the full calculation pipeline synchronously, right there on that thread.

⏰APScheduler background thread

Cron-style jobs: daily login, market open/close, opening-range refresh, checkpoint score digests — see Lifecycle.

🗄Postgres connection pool

asyncpg pool on the main event loop, used only by the paper-trading router and the candle-history writer — never by the live-tick path.

✓

Why one process, on purpose. The entire point of MarketState is a single shared source of truth that every reader — the broadcaster, the momentum score, the order monitor — can read instantly, in-process, with no network hop or serialization cost. Splitting "fetch" and "store" into separate deployed services would mean shipping every one of thousands of ticks/minute over a network boundary before anything downstream could use it — unnecessary latency and operational complexity for a single-operator dashboard at this scale.

10 — Client

Frontend: how & when data loads into the UI

Built for a stable frame rate across 170+ live rows, and to survive a mid-session page reload without a blank screen.

Load sequence, in order

1

Auth gate

GET /api/auth/me on mount decides Login screen vs Dashboard, based on the signed session cookie.

2

Instant paint from localStorage

Before any network round-trip resolves, the last cached snapshot frame (and the day's client-built candles) are read straight from localStorage so the screen is never blank — even if slightly stale.

3

WebSocket connect

useMarketStream() opens /ws/stream. The very first message is always a full snapshot frame, which immediately overwrites the warm cache with live truth.

4

Live deltas, surgical re-renders

Every message after that is a small delta — only the fields that actually changed. The store fans updates out per-symbol (useSyncExternalStore), so a tick on one stock only re-renders that one row, not the whole table.

5

Client-side candle building

The mini-candlestick chart is built purely from the LTP stream itself, tick-by-tick, in 5-minute buckets — no separate history fetch. Persisted to its own localStorage key so a reload mid-session doesn't lose the day's candles (discarded automatically if the cached day doesn't match today).

6

Self-healing

A sequence-number gap on a delta triggers a resync request for a fresh snapshot; 30 seconds of silence (no heartbeat) force-closes and reconnects with exponential backoff.

Rendering techniques

🎨Canvas bars

Pre-normalized coordinates rasterized on <canvas> — no per-pixel DOM, DPR-aware.

🧩React.memo rows

Re-renders isolated to rows whose data actually changed.

🔎Filters & sort

Signal · sector · day-range · signal-time, all client-side via useMemo.

📴Offline cache

Each snapshot mirrored to localStorage; on drop/standby it renders the last snapshot with a Closed/Offline badge.

11 — Operations

Daily lifecycle (APScheduler, IST)

If the process boots mid-session, it jumps straight to the correct state instead of waiting for the next cron tick.

☀

08:45 — Daily token refresh

Force-refresh a token (tries the refresh-token grant first, falls back to full TOTP login) — Mon–Fri.

▶

09:15 — Market open

REST backfill, flip market_open = true, launch the websocket ingest thread.

↻

09:46 — Opening-range refresh

Now that 09:15–09:45 has fully printed, re-seed the C1 ORB boundaries + the two breakout-quality gates in case the engine booted mid-candle.

≈

09:15–15:30 — Live

Ticks stream continuously; the Broadcaster fans delta frames to all WebSocket subscribers every 250 ms. The momentum-score checkpoint re-locks at 09:45 and every 30 min through 15:15.

■

15:30 — Market close

Close the websocket to conserve bandwidth (standby), square off any still-open simulated positions, and flush the day's last partial 5-min candle bucket to storage.

🧪

Dev override. FORCE_MARKET_OPEN=true in .env runs the engine regardless of the clock to exercise the full pipeline outside market hours.
